### Pydantic
正式开发时，是不是不使用 typedict 直接用 Pydantic 了？

11:26 AM

Worked for 2m 5s

不是。**正式开发中，`TypedDict` 和 Pydantic 通常会同时使用，各自负责不同层次。**

在 LangGraph 项目里，我更推荐这种分工：

```
外部输入 → Pydantic 校验
大模型输出 → Pydantic 校验
工具参数 → Pydantic 校验

Graph 内部共享 State → TypedDict
```

例如：

```
from typing import Literal
from typing_extensions import TypedDict
from pydantic import BaseModel, Field


# 大模型的结构化输出：需要运行时校验
class RouteDecision(BaseModel):
    route: Literal["search", "answer"]
    reason: str = Field(min_length=1)


# LangGraph 的内部共享状态
class GraphState(TypedDict):
    question: str
    route: Literal["search", "answer"] | None
    reason: str | None
    answer: str | None
```

节点中把两者连接起来：

```
def classify_question(state: GraphState) -> dict:
    decision: RouteDecision = router.invoke(state["question"])

    return {
        "route": decision.route,
        "reason": decision.reason,
    }
```

这里：

- `RouteDecision` 负责保证 LLM 输出符合规则。
- `GraphState` 负责描述节点之间共享的数据结构。
- 节点返回普通字典，让 LangGraph 合并状态。

为什么不直接把整个 State 都写成 Pydantic？因为 LangGraph 当前对 Pydantic State 有几个重要限制：

- 主要只在**第一个节点的输入**上执行运行时校验。
- 后续节点返回的更新不会自动逐次执行完整 Pydantic 校验。
- `graph.invoke()` 的最终结果仍然是字典，不是 Pydantic 实例。
- 递归校验还会增加一些性能开销。

因此，使用 Pydantic State 并不意味着“整个图的每一步都绝对安全”。这些限制在当前 [LangGraph 官方文档](https://docs.langchain.com/oss/python/langgraph/use-graph-api#use-pydantic-models-for-graph-state) 中有明确说明。

可以记住这个选择标准：

|场景|推荐|
|---|---|
|LangGraph 内部 State|`TypedDict`|
|API、用户等外部输入|Pydantic|
|LLM 结构化输出|Pydantic|
|Tool 参数|Pydantic|
|跨字段业务规则|Pydantic|
|只需要类型提示|`TypedDict`|
|需要默认值但不需要强校验|`dataclass` 也可以|

所以我们的课程项目继续采用：

```
GraphState      # TypedDict：管理图状态
RouteDecision   # Pydantic：校验大模型输出
```

这并非教学阶段的简化写法，而是一种适合正式项目的常见设计。




### fastapi


#### protocol
```
from typing import Protocol

class Calculator(Protocol):
    def calculate(self, a: int, b: int) -> int:
        ...
```

它表达的是：

> 只要一个对象有符合要求的 `calculate` 方法，就可以被当作 `Calculator` 使用。

因此下面这个类不需要继承 `Calculator`：

```
class Adder:
    def calculate(self, a: int, b: int) -> int:
        return a + b
```

它仍然可以传给：

```
def run(calculator: Calculator) -> int:
    return calculator.calculate(1, 2)

run(Adder())
```

区别可以这样记：

```
普通基类：必须显式继承，属于继承关系
Protocol：不要求继承，只要结构匹配，属于能力约定
```

参数名也不一定必须叫 `a`、`b`：Protocol 要求的是“调用方式兼容”，不要求代码逐字相同，最好保持参数名、类型和返回类型一致。

```
class Adder:
    def calculate(self, x: int, y: int) -> int:
        return x + y
```

当然，也可以显式继承：

```
class Adder(Calculator):
    def calculate(self, a: int, b: int) -> int:
        return a + b
```

但通常不是必须的。对于 Agent，`Protocol` 常用来描述“模型客户端应该具备什么方法”，方便替换真实模型和测试模型。

在 `Protocol` 中，三个点表示“这里只声明方法，不实现功能”，并非为了笔记简洁而省略,：未来真正使用它的类需要自己实现这个方法。
