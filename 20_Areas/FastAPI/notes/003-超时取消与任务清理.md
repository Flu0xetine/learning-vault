# 超时取消与任务清理

## 本篇概览

本篇围绕“等待模型时显示进度，超时后收尾”解释 `wait_for()`、`cancel()`、`CancelledError` 和 `finally`。超时会引发取消流程，而取消是请求，不能据此判断任务已结束；调用方应等待收尾，任务内部用 finally 释放资源。示例补全了原代码没有显式等待进度任务取消完成的环节。

## 学习来源

主要来源：[[20_Areas/FastAPI/codes/03-timeout-cancel.py|03-timeout-cancel.py]]；并发前提见 [[002-并发任务与结果收集]]。原文件完整表达了模型超时后请求停止进度提示的意图，下方示例为整理补充，不代表原文件已修复或已经运行验证。

## 原示例的流程

模型调用以 sleep 模拟五秒耗时，进度任务每隔约半秒打印一次。main 先创建进度 Task，再用 `wait_for(call_model(), timeout=2)` 等待模型。模型尚未返回时进度 Task 能继续推进；约两秒触发超时流程，捕获超时异常后打印提示，并在 finally 中取消进度任务。

原文件只执行了 `progress_task.cancel()`。这一步是发出请求，没有显式确认任务完成清理。虽然 `asyncio.run()` 结束时也会处理残留任务，应用自身仍应在拥有这个任务的作用域内明确等待收尾，不能依赖脚本退出替代业务生命周期管理。

## 整理后的完整示例

```python
import asyncio

async def call_model() -> str:
    await asyncio.sleep(5)
    return "模型回答"

async def show_progress() -> None:
    try:
        while True:
            print("仍在等待模型……")
            await asyncio.sleep(0.5)
    finally:
        print("进度任务已收尾")

async def main() -> None:
    progress_task = asyncio.create_task(show_progress())
    try:
        result = await asyncio.wait_for(call_model(), timeout=2)
        print(result)
    except TimeoutError:
        print("模型调用超时")
    finally:
        progress_task.cancel()
        try:
            await progress_task
        except asyncio.CancelledError:
            pass

asyncio.run(main())
```

示例按 Python 3.11+ 使用 `TimeoutError`；原文件写作 `asyncio.TimeoutError`，在这些版本中它是内建 `TimeoutError` 的别名。

预期行为是重复显示进度，然后输出超时信息并完成进度任务清理；进度打印次数取决于调度时机，不应断言某个固定次数。

## wait_for 如何超时

`wait_for()` 接收到协程后会将其安排为任务。若在限时内正常结束，就返回结果；超时则请求取消被等待任务，并等待取消完成，再向调用方抛出超时异常。

因此 timeout 并不是“到两秒时强行终止所有工作”的硬边界。清理耗时、代码阻塞事件循环等都可能使实际返回时间超过设定值。被调协程也应配合取消，通常不要吞掉取消异常后无限继续执行。

## cancel 与等待取消完成

```python
progress_task.cancel()  # 请求取消
await progress_task    # 等待它结束；取消成功时会抛出 CancelledError
```

取消通常在任务下次获得执行机会时注入 `CancelledError`，例如恢复其正在等待的 sleep。若任务正在执行阻塞代码，事件循环可能暂时没有机会处理取消；若任务已正常结束，再请求取消也不会把已完成结果改成取消。

上例 main 捕获的是自己主动取消的进度子任务的异常，以完成预期收尾。这不意味着应该在任何位置都忽略 `CancelledError`；任务内部若显式捕获它，完成清理后通常应重新抛出，让取消继续传播。

## finally 管理资源

```python
async def use_connection() -> None:
    print("打开连接")
    try:
        await asyncio.sleep(10)
        print("操作完成")
    finally:
        print("关闭连接")
```

这里用打印模拟资源生命周期。正常返回、异常或协作式取消导致代码退出 try 时，finally 都会执行；强制杀死进程等情形不在这个保证内。若取消发生在 sleep 期间，“操作完成”不会执行，但清理仍会执行。

## 与 Agent 服务的关系

未来模型调用可能很慢，辅助的进度提示不能在调用结束后一直存活。超时控制和子任务收尾应一起设计。取消本地协程也不能保证远端服务已经停止计算、停止计费或撤销已发生的工具操作，实际能力要看所用客户端和服务的约定。

## 复习自测

1. 五秒的模型模拟调用为何约两秒就进入错误处理？——外层 wait_for 限定等待，并触发取消流程。
2. timeout=2 是否保证程序严格两秒返回？——不保证，还受调度与取消清理影响。
3. 为什么 cancel 后还 await？——前者发请求，后者确认任务结束并接收结果或取消异常。
4. finally 的价值是什么？——在成功、异常和正常取消路径中执行清理。
5. 为什么这段代码能一边等模型一边打印？——进度是独立 Task，模型等待期间事件循环可以调度它。
