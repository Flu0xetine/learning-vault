# 上下文管理器与资源清理

## 本篇概览

`try/finally` 保证清理逻辑得到执行，`with` 则通过 `__enter__()` 和 `__exit__()` 封装“获取—使用—释放”流程。`@contextmanager` 可以把以 `yield` 为分界线的生成器包装成同样可供 `with` 使用的上下文管理器。本篇重点是资源释放、异常传播，以及类写法和生成器写法各自适合什么场景。

## 学习来源

本篇整理自 [[2026-09-20]] 的学习过程，以及 [[20_Areas/FastAPI/codes/04-try-except-finally.py|04]]、[[20_Areas/FastAPI/codes/05-with.py|05]]、[[20_Areas/FastAPI/codes/06-contextmanager.py|06]] 三份练习。会话中重点解决了“异常向外传播是什么意思”和“为什么不直接实现 `__enter__`/`__exit__`”两个疑问。异步上下文管理器本次暂缓，不在本文展开。

## 资源管理的基本问题

文件、数据库连接、锁和 HTTP 客户端通常都需要遵循固定流程：

```text
获取资源 → 使用资源 → 释放资源
```

如果直接顺序调用，使用资源时一旦抛出异常，后面的释放代码可能无法运行：

```python
resource = acquire_resource()
use_resource(resource)       # 此处报错
release_resource(resource)   # 无法执行
```

可靠的基本结构是：

```python
resource = acquire_resource()

try:
    use_resource(resource)
finally:
    release_resource(resource)
```

`finally` 的关键作用不是处理异常，而是无论 `try` 正常完成、抛出异常还是提前返回，都执行必要的收尾逻辑。

## `try`、`except`、`else` 与 `finally`

练习 04 分别处理了字符串转换失败和除零错误：

```python
try:
    number = int(text)
    result = number / divisor
except ValueError:
    print("无法转换成整数")
except ZeroDivisionError:
    print("除数不能为零")
else:
    print("success")
finally:
    print("本次计算结束")
```

执行规则是：

1. 先执行 `try`。
2. 出现异常时，从上到下寻找第一个匹配的 `except`；处理后不会回到 `try` 中断的位置继续执行。
3. `try` 没有抛出异常时才执行 `else`。
4. 无论前面走哪条路径，最后都执行 `finally`。
5. 如果没有匹配的 `except`，会先执行 `finally`，随后异常继续向外传播。

`finally` 必须与 `try` 组成完整语句，不能脱离 `try` 单独出现。

## `with` 封装了什么

上下文管理器对象实现两个方法：

```python
class ResourceManager:
    def __enter__(self):
        resource = acquire_resource()
        return resource

    def __exit__(self, exc_type, exc_value, traceback):
        release_resource()
        return False
```

使用时：

```python
with ResourceManager() as resource:
    use_resource(resource)
```

核心执行顺序是：

1. 创建上下文管理器对象。
2. 调用 `__enter__()`。
3. 把 `__enter__()` 的返回值绑定给 `as` 后面的变量。
4. 执行 `with` 代码块。
5. 离开代码块时调用 `__exit__()`。

因此，`as resource` 接收的是 `__enter__()` 的返回值，不一定是上下文管理器对象本身。只有在 `__enter__()` 返回 `self` 时，两者才是同一个对象。

练习 05 中的手动展开写法用于理解流程，但 `manager.__exit__(...)` 只是示意。真实调用时，Python 会根据代码块是否出现异常传入具体参数，并依据返回值决定是否继续传播异常。

## 什么叫异常向外传播

异常发生后，如果当前层没有处理，就会沿函数调用关系交给调用它的外层：

```python
def inner():
    raise ValueError("出错了")

def outer():
    try:
        inner()
    except ValueError as error:
        print("outer 捕获：", error)
```

这里 `inner()` 抛出的异常传播到了 `outer()`，再由外层的 `except` 捕获。如果所有调用层都不处理，异常最终到达程序最外层，程序终止并显示 traceback。

上下文管理器退出时会收到三个异常参数：

- `exc_type`：异常类型，例如 `ValueError`；
- `exc_value`：异常对象，例如 `ValueError("出错了")`；
- `traceback`：异常调用栈；
- 正常退出时三者都是 `None`。

`__exit__()` 的返回值决定异常是否继续传播：

```python
def __exit__(self, exc_type, exc_value, traceback):
    self.close()
    return False
```

- 返回 `False` 或 `None`：完成清理后，异常继续向外传播。
- 返回 `True`：告诉 Python 异常已经处理，不再向外传播。

也可以只抑制特定异常：

```python
return exc_type is ValueError
```

但不应无条件返回 `True`，否则可能悄悄隐藏程序错误。资源管理器通常应当完成清理，然后让未知异常继续传播。

## 为什么不总是直接实现 `__enter__` 和 `__exit__`

直接实现完全正确。当资源本身是自己设计、具有多个方法和内部状态的对象时，类写法很自然：

```python
class DatabaseConnection:
    def __enter__(self):
        print("连接数据库")
        return self

    def query(self):
        print("查询数据")

    def __exit__(self, exc_type, exc_value, traceback):
        print("关闭数据库连接")
        return False
```

`@contextmanager` 解决的是另一种情况：资源来自第三方库，不方便修改其类；或者管理逻辑很短，不值得专门创建一个管理器类。

```text
复杂、有状态、由自己设计的对象 → 类写法
简单的获取与释放包装           → @contextmanager
```

二者能力上不是高低关系，只是组织代码的方式不同。

## `@contextmanager` 与 `yield`

练习 06 使用 `contextlib.contextmanager` 包装第三方连接：

```python
from contextlib import contextmanager

@contextmanager
def database_connection():
    connection = third_party_library.connect()
    try:
        yield connection
    finally:
        connection.close()
```

使用方式与类版本相同：

```python
with database_connection() as connection:
    connection.query()
```

可以把执行过程理解为：

```text
yield 前       → 进入上下文，获取连接
yield 的值     → 绑定给 as 后面的 connection
暂停生成器     → 执行 with 代码块
恢复生成器     → 离开 with，执行 finally 并关闭连接
```

`@contextmanager` 的作用是把这个生成器包装成拥有 `__enter__()` 和 `__exit__()` 协议的对象。它不是让资源对象自身突然拥有这两个方法，而是在资源外面增加了一层管理器。

清理逻辑仍应放入 `finally`：

```python
try:
    yield resource
finally:
    release_resource(resource)
```

这样即使 `with` 代码块抛出异常，释放逻辑依然会执行。若没有显式捕获并抑制异常，异常会在清理后继续向外传播。

## 与 FastAPI 的关系

FastAPI 后续会大量使用相同的生命周期思想。例如数据库依赖通常在请求前创建 session，把它提供给路由，最后关闭：

```python
def get_session():
    session = create_session()
    try:
        yield session
    finally:
        session.close()
```

当前阶段先掌握同步执行顺序即可。异步数据库和 FastAPI 应用生命周期会把它扩展为 `async with`、`__aenter__()`、`__aexit__()` 与 `asynccontextmanager`，但基本目标仍然是安全地获取和释放资源。

## 易错点

1. `finally` 保证尝试执行清理逻辑，但如果 `finally` 自己又抛出异常，清理仍可能失败，并可能覆盖原异常。
2. `__exit__()` 返回 `True` 不是“退出成功”，而是“抑制异常”。
3. `as` 后变量来自 `__enter__()` 的返回值，不一定是管理器本身。
4. `@contextmanager` 装饰的生成器通常应当只 `yield` 一次。
5. `yield` 后直接写清理代码不如放在 `finally` 中可靠。
6. 上下文管理器负责某段执行范围内的资源生命周期，不等同于长期任务状态持久化。

## 复习自测

1. 为什么资源释放通常写在 `finally`？——因为正常结束和异常路径都需要执行它。
2. 没有匹配的 `except` 时，`finally` 会执行吗？——会，执行后异常继续向外传播。
3. `as value` 中的 `value` 从哪里来？——来自 `__enter__()` 的返回值，或 `@contextmanager` 中 `yield` 的值。
4. `__exit__()` 返回 `False` 表示什么？——不抑制异常，让异常继续交给外层。
5. 为什么第三方连接适合用 `@contextmanager` 包装？——无需修改第三方类，也能集中定义获取和释放流程。
6. `@contextmanager` 是否比类写法更强？——不是；它只是简单场景下更精简的组织方式。
7. 为什么清理代码仍要放进 `finally`？——保证 `with` 代码块抛出异常时仍执行清理。
