# 协程与事件循环的等待机制

## 本篇概览

本篇解释 `async def`、`await`、`asyncio.sleep()` 和 `asyncio.run()` 的分工，重点回答“await 是否启动事件循环”和“暂时不能完成是什么意思”。调用异步函数先得到协程对象；执行过程中遇到真正的挂起点，当前 Task 才交出控制权。掌握库的异步接口及正确调用方式，是未来编写 FastAPI / LangGraph Agent 的应用基础。

## 学习来源

主要来源：[[20_Areas/FastAPI/codes/01-async.py|01-async.py]] 的代码与注释；本次会话用于补齐其中“暂时不能完成”的空白及相关追问。原文件保持原样，下面为整理后的说明和示例。

## 从函数到协程对象

```python
import asyncio

async def greet() -> str:
    await asyncio.sleep(2)
    return "你好"
```

`async def` 定义协程函数，允许其内部使用 `await`，但不保证函数一定发生等待，也不保证其中所有操作都不阻塞。

调用 `greet()` 得到协程对象，此时函数体尚未执行，返回的不是字符串“你好”。协程对象与独立调度的 Task 要区分；需要独立任务时见 [[002-并发任务与结果收集]]。

原文件顶层写了 `result = greet()`，但后面又调用了另一个 `greet()`。前一个协程并没有因此被执行；若一直未等待或调度它，可能出现“coroutine was never awaited”警告。演示“调用得到对象”有教学意义，但完整程序应处理它或不创建这个闲置对象。

## 一个完整的入口与等待链

```python
import asyncio

async def greet() -> str:
    await asyncio.sleep(2)
    return "你好"

async def main() -> None:
    message = await greet()
    await asyncio.sleep(2)
    print(message)

asyncio.run(main())
```

普通脚本中，`asyncio.run(main())` 创建并运行事件循环，负责最外层异步程序的运行与收尾。`main()` 进入 `greet()`，先等待约两秒，再在 `main()` 中等待约两秒，因此约四秒后输出“你好”。写了 `async` 并不会把这两段等待自动重叠。

普通 `.py` 文件不能直接在顶层使用 `await`，应写在 `async def` 中；某些交互环境支持顶层 await，是环境提供的便利。已有事件循环的框架环境应按框架方式调用异步代码，不重复嵌套 `asyncio.run()`。

这里的调用链属于同一个 Task：

```text
main
  └─ await greet()
       └─ await asyncio.sleep(2)
```

直接 await 一个协程不会自动把它创建成第二个独立 Task。

## 曾经困惑：await 是不是启动事件循环？

**当时的理解（已纠正）**：执行到 await 后其他任务才开始，因此 await 启动了事件循环。

观察到了真实的控制权切换，但“启动”用在这里不准确。事件循环早已在运行，否则也不会执行到 `main()` 中的这行代码。当前任务发生挂起时，控制权回到事件循环，它再调度其他就绪任务。

```text
run 启动事件循环 → 执行 main → 进入 greet
→ sleep 登记计时并挂起 → 事件循环处理其他工作
→ 计时就绪 → 重新调度当前任务 → greet 返回结果
```

如果没有其他可运行任务，事件循环等待计时器或 I/O 等事件，不需要空转。原注释“循环为空”应理解为“没有其他可运行任务”，当前任务及其等待关系仍然存在。事件就绪也不意味着当场立即恢复，仍需事件循环调度。

## 曾经困惑：“暂时不能完成”的边界

它指函数内部或更深层调用中遇到了真正的异步等待点，不专指最后一行 `return`。例如上面 `greet()` 停在 `await asyncio.sleep(2)`，等待计时就绪后才继续执行返回语句。

对本次使用的 asyncio 接口，可以这样记：等待对象尚未就绪时，异步实现会挂起当前任务；结果就绪后，任务才能继续推进。仅仅“执行很耗时”不足以判断会不会挂起。

| 操作 | 对当前事件循环的影响 |
| --- | --- |
| `await asyncio.sleep(2)` | 挂起当前任务，允许运行其他任务 |
| 使用异步网络客户端，数据尚未就绪 | 通常挂起，等待 I/O 就绪 |
| `time.sleep(2)` 放在异步函数中 | 阻塞当前线程，事件循环无法推进其他任务 |
| 同步网络请求放在异步函数中 | 等待网络时仍可能阻塞事件循环 |
| 在当前线程持续进行大量计算 | 没有主动挂起时会一直占用执行权 |

`await` 本身不保证每次切换任务：

```python
async def immediate() -> int:
    return 1

async def main() -> None:
    result = await immediate()
    print(result)
```

这里能直接取得结果，不需要挂起。进一步的边界是，不能把“必须等待外部事件”当作所有让出控制权行为的唯一条件：`await asyncio.sleep(0)` 也会主动挂起，给其他任务运行机会。应用阶段无须研究这些底层协议，但应避免把教学简化当成绝对规则。

## 应用时需要了解多深

本次最后澄清的实际需求是：使用一个库时，先查文档确认它提供同步还是异步接口、如何等待结果，通常不用阅读内部如何登记网络事件。`async def` 不会自动把函数内的同步请求改造成异步请求，因此自己组合代码时仍需留意阻塞调用。

## 复习自测

1. `greet()` 为什么不是“你好”？——它先创建协程对象，函数体尚未执行。
2. `await greet()` 是否启动事件循环或自动创建新 Task？——都不是；本例在当前 Task 中沿调用链执行。
3. 没有其他任务时，异步等待是否仍然有意义？——仍按异步机制等待，只是本例没有其他任务能利用等待时间，因而没有并发提速。
4. 长时间计算为什么不自动让出执行权？——耗时本身不是调度信号，代码没有进入挂起点。
5. 实际使用库时必须定位每个内部等待点吗？——通常不用；确认异步 API 的契约并正确调用即可。
